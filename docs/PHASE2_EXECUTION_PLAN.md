## 用户确认的目标与成功标准

- 主展示不再绑定27B或2bit。按本机24GiB统一内存、质量、通用性、开发者生态及DS机制适配成本，首选 `mlx-community/Qwen3.5-9B-8bit`，同模型4bit作效率对照，Qwen3-14B-4bit作低适配成本后备；允许Codex根据预先定义的质量/内存/延迟实测自主调整型号与量化，并汇报证据，无需再次确认。
- 核心思路与实现方法必须直接来自 DS 的公开设计方案或源码机制，并在 Mac 上形成真实执行路径；MLX 是 Apple Silicon 执行后端。允许针对统一内存、Metal 和 MLX 重新实现，不要求搬运原始代码、保留原语言或逐行一致。只有借用名称、泛泛“受启发”或通用优化，不满足这一条件。

- 以“DS 设计机制核实 → Mac 实现方法对应 → 正确性与机制测试 → 性能消融 → 竞品对照 → 展示”组织主线。不是先定性能结论再选择数据。

## 1. 能力优先的24GiB Mac主展示选型

2026-10-21用户最新要求：不绑定27B/2bit；内存可用性、通用性和适配难度接近时，优先模型能力与可信跑分，不能因现有代码容易适配就选弱模型。

**主展示首选 `mlx-community/Qwen3.5-9B-8bit`**，公开API核验revision `16daa4818c54ce5f5436f929d52542eb65bbed9d`，权重文件总计10,426,592,423 bytes（约10.43GB/9.71GiB，含仓库视觉部分，不等于纯文本运行内存）。**同模型4bit是效率/量化质量对照，Qwen3-14B-4bit是低适配成本后备与DS推测控制模型。** 详见 `PHASE2_MODEL_SELECTION.md`。这些是执行选择，尚未本机加载验证；本轮不将模型锁或registry标为已验证。

### 选择规则与模型分工

先判断24GiB下能否稳定运行、合法可用、执行路径是否可实现；通过后优先比较可信能力评测和本机任务质量。质量相近才用延迟、内存和开发成本决胜。跑分需记录版本、量化、thinking/采样、token预算与评测工具，不能把不同协议分数混排，不能拿官方原精度成绩替代本机量化表现。

| 角色 | 模型与量化 | 依据与用途 |
|---|---|---|
| 能力优先主展示 | Qwen3.5-9B MLX 8bit | 较新的通用/代码/指令评测证据；更高位宽作为减少量化损失的起点，效果仍待实测 |
| 同模型效率对照 | `mlx-community/Qwen3.5-9B-4bit` | 同题评测4bit相对8bit的质量损失与速度；若质量无实质差异且速度明显更好，可自主改为主展示 |
| 工程后备/调度控制 | `mlx-community/Qwen3-14B-4bit` | 标准注意力KV可trim，适配已有DS预算验证路径更容易；不能据此声称模型能力胜过9B |
| 更轻量后备 | `mlx-community/Qwen3-8B-4bit` | 24GiB多应用共存、低延迟及第二尺寸泛化；只有满足实际任务质量才采用 |
| 代码专项对照 | `mlx-community/Qwen2.5-Coder-14B-Instruct-4bit` | 可执行代码修改与单测，检查通用模型的开发实用性 |
| 快速回归 | 已锁定Qwen3-4B/0.6B 4bit | 正确性、成本与调度测试，不替代主展示结论 |

27B 2bit降为历史实验，保留报告；不再为了主线继续救其质量或下载替代27B。30B/35B MoE需驻留全部专家权重，不能用活跃参数量推断内存，也不作为24GiB首选。9B的多模态能力不是本项目默认已实现的能力：先做文本展示，图片支持只有完成实际端到端验证后再宣传。

### 内存与上下文

本轮实测物理内存25,769,803,776 bytes（24GiB）。9B 8bit全仓权重约9.71GiB，为系统/IDE/浏览器规划约6GiB余量，其余用于KV、循环状态、prefill、allocator及缓存；这是规划，不能宣称已完成压力测试。按官方配置，9B有8个全注意力层，4 KV heads/head_dim256，2-byte KV约32KiB/token，4K约128MiB、8K约256MiB；另有24层循环状态、视觉权重处理及临时buffer，必须实测。

14B后备权重8,307,898,514 bytes（约7.74GiB），40层/8KVheads/head_dim128的2-byte KV约160KiB/token，4K约640MiB、8K约1.25GiB；0.6B草稿额外约0.31GiB权重及4K约448MiB KV。4bit权重不等于4bit KV。模型峰值、RSS、系统内存压力、swap增量分别记录，不能重复相加RSS和Metal。

先做4K总上下文/单请求，缓存512MiB，再测2K/4K/8K与并发2/4；上下文长度和并发容量需报告实测边界。一次available-memory读数不代替实际可运行性；若持续swap/尾延迟异常，调整缓存、分块、量化或后备型号，记录原因。

### 执行和验收

1. 锁定模型revision、量化配置、tokenizer/template、SHA256、许可证。先加载9B 8bit文本baseline并验证MLX-LM sanitize与原生输出；只读metadata不是加载证据。
2. 建立公开能力资料表和本机质量集。公开跑分优先同协议、同版本，区分官方自报/独立复现/本机实测。至少覆盖代码（LiveCodeBench版本固定及可执行修复测试）、指令（IFEval）、知识推理（MMLU-Pro/GPQA的合适可访问题集）、中文与多轮。资源受限时预先固定子集并明确标为子集，不能声称复现全榜。
3. 预先固定本机开发集和保留集，记录任务成功率、错误、重复退化、完整输出和完成正确任务所需时间。代码评分用单测，不用模型自评；单个综合分不能掩盖代码或中文明显退化。质量差异附样本量/不确定性，不能用几个样例声称能力相同。
4. 9B 8bit/4bit与14B 4bit同题比较；thinking/non-thinking分别测，按官方建议核对采样与生成预算。当前引擎若仅greedy，另用原生推荐配置判断质量，补齐必要采样支持后才能宣称该配置端到端可用。模型原榜单分数不能直接写进本机性能图。
5. DS路线分开推进：在14B/4B可trim模型验证成本/验证预算机制；主展示9B需实现精确混合状态checkpoint/replay或核验可用MTP/兼容draft，亦可先落地其他具体来自DS设计的机制。不能把Qwen3-0.6B直接当9B兼容草稿；词表、special IDs、模板和状态语义均须验证。MTP有配置字段也不代表权重或执行已支持。
6. 14B路线可试已锁定0.6B及核验后的1.7B草稿。先消除预算中草稿尺寸硬编码，按实际metadata计内存；测接受率与完整周期，不能只看验证步骤加速。两条路线已有代码与报告保留，不重做已成立实验。
7. 依据实测自主定最终模型：若9B 8bit与4bit质量接近，选更有效率的版本；若9B主展示暂无法实现有效DS优化，继续适配，同时可用14B汇报工程进展，但不能把14B收益算到9B或仅以适配方便结束主模型选择。只有明确技术障碍、质量/延迟与收益证据支持时才切换后备，并在节点汇报理由，无需请示。
8. 主展示通过质量与真实运行后更新两份模型锁、registry、CLI示例和API/SSE/UI。所有竞品使用相同最终主模型/量化重跑。新模型提升属于选型收益，DS开关改善才属于框架贡献；两者分别展示。

验收：实际模型/量化、能力跑分来源及可比性、本机质量和内存结果、主模型真实API/UI、DS机制运行证据与公平竞品结果。两条路线均需按实际完成度汇报；只在旧模型上有收益不能完成主展示验收。

## 2. 落地 DS 成本驱动的验证预算设计（首选主线）

设计依据与可用参考实现：

- `mtp_varlen.hpp:20–42` SamplerRuntimeEstimator，滑动中位数与最小样本门槛。
- `:48–131` ForwardRuntimeEstimator，启动曲线残差、按graph size分组、中位数聚合。
- `:133–275` MTPVarlen，性能曲线 + expected accepted tokens + sampler成本选验证预算。

执行：

1. 建立 `src/deepinfer_mac/ds/` 和设计对应清单。保留 DS 成本估计、接受收益估计与验证预算决策之间的关系；记录设计来源。实际复用代码时另保留许可证、归属及 commit/hash。
2. 按 Mac 执行开销和可维护性选择 Python、C++ 或其他适用实现；无需为了证明来源而引入生产 C++ 绑定。针对目标函数、滑动统计、样本门槛及决策规则构建独立参考；原始 C++ 适合作为可复用的调度 oracle，不是所有模块的强制实现形式。
3. 从 MTPVarlen 提取明确输入/输出与状态转换；复用原码时适配 Sequence/TORCH_CHECK边界，重新实现时映射到本地请求状态。先构造离线调度参考。覆盖空曲线、样本不足、不同graph sizes、负残差、相同置信度tie、batch=1/N、无草稿、schedule/process轮次差及不同长度。
4. 保留 N−2 / N−1 接受率隔离逻辑，不能偷用当前未验证token的信息。记录每次预算选择可回放输入/输出。
5. 没有 DS Confidence Head 时，只能把历史接受率作为独立输入适配层，称“DeepInfer MTPVarlen-derived scheduler with empirical acceptance”。不能称完整 DSpark。
6. 在真实执行路径中使用上述 DS 机制的 Mac 实现，加入同模型、同草稿、同执行循环下 DS-derived / 旧policy / tuned-fixed / baseline 的消融，证明贡献来自调度，而不是顺带修正的同步开销。
7. 将单请求 n=1 与未来并发 N>1 分开评估。若收益主要来自跨请求分配，先做离线多请求调度回放，再按真实负载决定是否加入批执行，不能把串行FIFO叫连续批处理。

验收：未改动的算法语义与独立参考一致；有意平台适配单列差异、原因及不变量测试，不能以适配为由跳过验证。生产路径实际执行 DS 对应机制，并提供开关消融。原码复用与依据设计重新实现均可通过；只有 vendor 文件或设计说明、没有实际执行与机制证据，不能通过。

## 3. 从已发现收益继续优化

### 3.1 精确检查点与真实会话复用

首版完全重复prompt收益来自跳过prefill。分支仅保存第一个chunk导致命中不足。本轮已实现可选 `checkpoint_interval_tokens`，默认0保持原行为；512间隔实验已记录，尚非正式默认。

- 对照首版、固定间隔、system/turn边界、MLX-LM原生LRU/分段缓存，保持相同总预算。
- 在真正的对话续接处保存“已经被模型消费的token对应状态”，处理最后未消费token、EOS、template变化、取消和并发分支。
- 混合recurrent状态仅能恢复精确快照后重放后缀，不能任意trim；不要移植DS的近似SWA replay名称掩盖语义差异。
- admission以预计省下的prefill时间/快照成本/字节复用率为实验方向，测查找、克隆、写入与淘汰开销。
- 可学习DS缓存分层/查找与搬运解耦的设计，但DS生产KV服务没有完整公开；可依据官方设计重实现，但必须补充具体方法、Mac执行对应和机制消融；若证据仅支持泛泛架构参考，则不能计作核心 DS 贡献。

验收：真实多轮和改尾分支的TTFT/任务总时长、全部输出对照、snapshot成本与内存；不能只用1740输入+2输出的重复例子作为宣传主图。

### 3.2 执行循环与成本测量

本轮 `defer_draft_sync=True` 为opt-in实验：沿锁定MLX-LM模式保留device数组，统一读取验证结果。它来源于MLX-LM，不能标成DS移植。原同步路径仍保留。

- 固定k对比原生固定循环、旧适配器、新适配器，独立于policy。预算相同、权重相同、完整输出比对。
- 重做异步路径计时：combined draft+verify 不能被拆成伪GPU时间；同时测完整周期，包括调度、host转换、回卷、输出和诊断。
- 将草稿catch-up与稳态样本分开；永久disabled改为有期限/负载变化时重新校准，避免短问答导致后续代码任务永远不用草稿。
- 性能快路径关闭逐轮重诊断，采样profiling单列；旧/新路径accept/reject/EOS/取消用现有测试双跑。

验收：控制流与真实模型测试通过，运行时开销至少不劣于原生路径后再评价DS-derived调度。不得把“追平原生”宣称为“超越原生”。

### 3.3 数值分歧定位

第一阶段推测输出出现真实量化模型差异。固定首次分歧位置，比较相同历史单token/批验证logits、top-2 margin、cache offsets、不同执行路径；记录误差来源。不要把所有差异未经验证就归因于浮点。

对量化浮点差异采用双轨证据：精确一致样本用于等价性能对比；非一致样本保留完整任务质量评测，不能删除失败样本提高平均收益。

第一层严格对照：

- 原生 MLX-LM 当前锁定版本的生成与server/cache能力，不关闭对手缓存/合理分块等已具备优化。
- oMLX 或另一成熟MLX服务引擎，先核实官方源码、安装和同一主模型及量化版本的支持；版本与配置固定。若不支持该模型，明确兼容差异并选择双方实际支持的模型另测，不给对手记虚构零分。
- 同机、同repo+revision、同权重、同模板、同请求序列、同采样、同缓存预算及并发度。先分别热身，轮换顺序，性能运行独占GPU；分别报告冷加载/暖模型冷KV/热KV。

第二层产品体验对照：

- 本机已有 Ollama，可与 llama.cpp 路线比较，但GGUF与MLX不同量化配方必须披露；使用质量匹配或相同基础模型的质量-延迟曲线，不能称纯引擎公平加速。
- 2K/4K/8K输入、短/长输出、代码/中文、重复系统提示/真实续聊/改尾分支/多会话；开发集调优后锁参数，在保留集报告。
- 测TTFT、ITL、任务总时间、输出速度、质量通过率、缓存命中、峰值与失败。bootstrap按prompt/会话聚类，不把同一prompt重复测量当独立任务。
- 每项核心优势必须有 DS-derived feature on/off 消融；若改善来自MLX复用或通用缓存，来源单列，不能单独作为DS设计机制有效落地的证明。

直观产物：同输入并排录屏、完整耗时条、首token时间线、质量/性能表、原始JSON下载、一条命令复现；注明是否为回放、机器和完整配置。默认首页只呈现验证集上成立的优势，同时链接不利结果。

验收：至少两个主要对照上的具体场景优势成立且可复现。未达到时发布实验更新，不将这一目标标记完成。这个门槛是结果标准，不是禁止继续工作的审批节点。
