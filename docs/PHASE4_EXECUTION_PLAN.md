# 第四阶段：让 DeepInfer 设计成为 MLX 上可感知的性能优势

日期：2026-10-21。本文是待执行设计，不表示第四阶段功能或性能已交付。

## 产品定义与执行方式

DeepInfer Mac 是 **基于 MLX、采用 DeepInfer 调度设计的通用推理框架**。模型由适配器接入，示例模型只是演示配置。复用 MLX-LM 模型、算子、批处理和缓存；项目独立价值集中在完整成本驱动的验证预算、跨请求资源分配、状态流水和交互服务策略。

第四阶段由 Codex 连续实现、测试、诊断和迭代，不设日历排期，不逐项请求确认；关键节点汇报结果后继续。一次只运行一个 GPU 测量任务，保留用户已有服务和资源保护。资源暂不满足时继续接口、CPU 验证、文档与贡献补丁工作；不反复要求用户释放内存。失败候选保留诊断后切换方案，不无限重复相同实验。

本次只交付计划。进入执行后，正常仓库开发与本地验证连续推进；上游 PR 先形成可审查补丁和说明，再按届时用户授权提交。发现上游缺陷不等于获准联系维护者，不把 PR 合并或项目热度列作可保证结果。

## 成功定义

同时交付三种价值：

1. **技术价值：**至少一个来自 DS 设计的机制，在预先冻结的代表性负载上，相对原生 MLX-LM 和 oMLX 均有稳定净收益；通过关闭该机制的同引擎消融证明来源。
2. **产品价值：**统一模型接入、好用的 API、直接可运行 demo、三个维度的结果看板，以及积极清晰的双语主页。
3. **生态价值：**至少一份独立于本项目品牌和完整调度系统、具有复现与测试的上游贡献候选。是否提交、被接受分别记录。

性能目标是待验收目标：任务耗时下降至少 15%；或并发 p95 TTFT/ITL 下降至少 20%且吞吐不回退；或固定延迟 SLO 下可持续吞吐提升至少 20%。一个预声明主指标满足即可形成首个明确卖点，其他指标完整展示。单纯少算 token、比自家旧版本快、靠更弱量化或只提高队列长度均不满足。

通用接口与性能覆盖分开：至少两个模型家族验证普通接入，Dense 与混合状态均有能力声明和正确回退；首个加速可以有明确架构/负载范围，不因此将整个框架绑定单模型，也不将一组结果宣传为所有模型普遍更快。

## 1. 统一执行入口与可靠的路径选择

**实现：**沿用 adapter/engine/service 配置，将 baseline、native batch、联合投机视为同一运行时的执行策略。提供本项目新增的策略选择接口，支持固定策略和自动策略；保持目标权重、模板、采样和模型 ID 一致。未知能力默认走原生路径。不要创建另一套张量框架。

自动策略需把“无投机”作为真实候选；冷启动使用原生路径，探索成本计入端到端结果。按模型/量化/草稿/上下文/并发/缓存类别/执行策略隔离成本，使用收益余量和滞回避免频繁切换。从投机切回原生必须先提交已验证前缀，恢复目标状态并正确处置草稿状态，不能只切一个 flag。

**先处理数值问题：**从 `docs/DENSE_FASTPATH_EXPERIMENT.md` 的相同历史、相同分段 oracle 继续定位 fast-trim 差异；分别检查 offset、mask、未消费尾 token、merge/extract 与浮点形状差异。旧 frozen tolerance 保留。如果需要新建数值误差政策，先定义指标和依据、使用新数据验证，不改写历史失败。未通过的优化保持实验路径，其他主线继续。

**验收：**普通加载和服务跨家族；Dense/混合状态能力与回退；切换、取消、EOS 和恢复边界测试；greedy 序列检查与相同历史 logits 检查；涉及非 greedy 时另做采样分布验证，不能借 greedy 通过直接开放。

**参考：**`adapters.py`、`engine.py`、`continuous.py`、`joint_service.py`、`hybrid_speculative.py` 以及已有相应测试。关键节点汇报：新增默认可用能力、保持实验的能力和依据。

## 2. 核心差异：完整成本感知的联合验证预算

**DS 来源：**`mtp_varlen.hpp` 的期望产出/成本优化、运行反馈及两代历史；`schedule_mtp_varlen.py` 的连续前缀概率、跨请求排序和映射。

**实现：**保留已验证算法参考，补齐服务路径的成本采集、曲线加载与有限在线更新。记录完整周期，包括草稿、验证、恢复、补算、分桶/合并和主机工作；测量附加开销单列，不能只优化目标 forward。

重点检验当前设计的成本失配：相同总验证 token 数，在一个大桶与多个小桶上的成本可能不同。为 Mac 适配增加桶数、桶形状和上下文组成描述；用有限候选比较共享长度、少量长度桶和原生执行。任何偏离原 DS 优化器的分组成本修正单列为平台扩展，并用原规则消融，不能默认为 DS 原始实现。

置信度先利用已有已完成轮次的经验估计，记录冷启动、被截断观测和可靠性；再比较轻量校准能否提高接受预测。`ConfidenceProvider` 保留可插拔接口；只有具备兼容权重和独立收益证据时才接训练式 ConfidenceHead，不把草稿 softmax 概率当已校准接受概率。

减少无效工作不仅要压缩验证，也要检查预算确定后是否仍生成过量草稿。按分配长度分组生成或使用少量深度档位，比较省下工作与新增调用的净成本。新请求无历史与高低接受请求混合是必测场景。

**验收：**固定共享深度、DS 原规则、DS+Mac 成本适配、native 四路同循环消融；报告预算、实际 shapes、草稿/验证/恢复工作量、接受数、完整耗时和状态正确性。冻结开发选择后再跑新保留任务。关键节点汇报是否产生首个净收益，不能只展示 30.3% 位置减少。

**参考：**`docs/PHASE3_BUDGET_REFERENCE.md`、`docs/PAIR_COST_EXPERIMENT.md`、`ds/joint_budget.py`、`varlen_verify.py` 及现有 cost/pair 实验脚本。

## 3. 第二条收益主线：并发响应与缓存工作预算

**DS 来源：**`scheduler.hpp` 的 token/context/cache 联合调度、prefill/decode 预算；`block_manager.hpp` 的生命周期与共享状态原则。

**实现：**在 `MLXBatchSession` 与现有 worker 上增加基于每轮工作量、缓存水位和等待时长的准入与 prefill 配额。优先解决长输入使已输出会话停顿，以及短请求等待长 prefill 槽位的问题。先使用原生分块与连续批处理；确需更细切分时，依据真实上游可用接口实现，不假设支持任意暂停。

统一 target/draft 缓存身份和失效边界，减少可证明不必要的快照与复制。复用现有原生 LRU；原生 cache 命中收益与 DS 调度增益分开记账。只有普通前缀复用有正确性后，才扩展分支共享；不在本轮重写完整分页注意力系统。

**验收：**固定到达轨迹下的聊天+长文档、异构接受率并发、重复前缀三类负载；并发 1/2/4 起步，资源允许再扩展。同时报告 p50/p95 TTFT、最大/尾部输出间隔、吞吐、拒绝/超时/取消、内存与饥饿情况。固定延迟 SLO 下报告最大可持续完成吞吐，避免靠积压制造并发优势。

**参考：**`continuous.py:AdmissionBudget/MLXBatchSession`、`server/continuous_worker.py`、`server/joint_worker.py`、`cache.py`、`docs/CONTINUOUS_EXECUTION.md`。关键节点汇报并发收益及吞吐代价。

## 4. 按时间线决定 ZOS 状态流水与 Metal 优化

**DS 来源：**`worker.py:execute_model_step/_correct_seqlens_qk` 与 `zos.cpp`，核心是跨轮请求映射和状态修正下的执行重叠。

先复用现有 default-off profiling，结合实际可用设备时间线定位 host 等待、结果物化、模型调用与缓存复制。主机 wall 区间不能冒充 GPU kernel 时间。若主机等待有足够优化空间，再实现有限的跨轮元数据缓冲、设备侧接受长度/位置修正、CPU 后处理与后续提交重叠；始终维护取消、slot generation、EOS 和资源生命周期。

现有 MLX-LM async_eval 是基线。新增价值必须在“动态预算+动态请求进出”场景单独证明。若瓶颈仍是草稿或恢复模型计算，就继续优化对应路径，不为了 ZOS 名称强行增加异步复杂度。

`allocate_mlx` 当前使用两两比较排名，候选数量增长会放大开销；只在 profile 证明显著时比较稳定排序/选择或小型 Metal 算子，保留 DS tie/remap/前缀不变量与 CPU oracle。YoCo/CED 和多设备专家复制仍保留扩展接口，本轮不硬搬到不匹配模型。

**验收：**同源同步/异步消融，完整延迟和吞吐、同步次数及正确性；至少覆盖请求加入、退出、取消和拒绝。无收益分支不进入默认路径。参考 `docs/DS_DESIGN_MAPPING.md` 与阶段 2/3 已有执行入口。

## 5. 公平性能与质量证据

新建可公开的自写任务集、到达轨迹、JSON 协议和统一执行器；不继续用已暴露 heldout 调参。主演示沿用能力较强的已验证配置，研发小模型用于快速定位，二者数据分开。

- 比较原生 MLX-LM、oMLX、我们固定策略和自动策略；以各基线合理调优后的适用模式为对手，不刻意关闭其批处理、缓存或兼容加速功能。
- 分开原始执行层与端到端 API 结果。原生只有执行 API 时使用公开的薄服务壳并明确开销，不拿直调函数与 HTTP 混比。
- 同模型 revision、量化、模板、提示、输出/停止和采样语义；跨服务优先采用自然 EOS 协议。固定忽略 EOS 诊断保留内部使用。
- 至少三次独立进程，轮换框架顺序；按提示/到达轨迹聚类统计区间，不能把 token 或周期伪装为独立样本。保留所有失败与资源排除原因。
- 冷/热缓存、冷启动/稳态分别统计，自动探索及fallback开销不得扣除；开发集选择完成后冻结参数及主指标。
- 开销报告明确为峰值内存、处理工作量或主机成本；没有能量测量不宣称更省电，没有费用模型不声称价格优势。
- 保留现有严格正确性检查，增加长输出、不同上下文和常见开发者任务；性能优化不以降低模型质量换取。

关键节点交付 `benchmarks/reports/phase4-competitive-summary.json`、完整复现入口和同引擎消融。达到目标的指标写入展示；未达到时记录最优有效结果及瓶颈，继续候选优化，不降低目标或改名宣称完成。

## 7. 上游贡献与最终交付

候选按实际证据排序，不为了曝光发送空泛 PR：

1. **MLX-LM 行为复现/回归测试：**从批处理形状差异、缓存 merge/extract/trim 边界中提取最小案例。先确认是不是预期浮点差异；只有明确问题和可验证修复才提交 bugfix。
2. **公开动态 prefill 配置接口：**本地 `continuous.py:217–218` 为调整 chunk 同时更新 `BatchGenerator.prefill_step_size` 和私有 `_prompt_batch.prefill_step_size`。优先核对最新上游是否已有解决方案；否则准备公开 setter/方法候选，覆盖在途与后续 batch 的一致性及边界行为。这是已发现的具体集成需求，不预判它属于上游缺陷。
3. **可独立复用的执行原语：**若本轮证明缓存操作或草稿提交的冗余成本，可提取不依赖本项目的窄接口改善，附基准和兼容性测试。完整 DS 调度器先保留本仓库，避免向上游提交巨大系统重构。
4. **生态集成示例：**如果 oMLX/其他 MLX 项目当前提供适用扩展点，准备联合预算适配例；先核验当前接口与许可，避免叠加两层 scheduler 或重复拥有 KV。

产出 `docs/UPSTREAM_CONTRIBUTIONS.md`：目标仓库/精确 base、现有相关 issue/PR、问题、最小补丁、测试、性能、兼容性和提交状态。准备至少一个可审查候选；若事实证明没有合适上游改动，则交付明确调查与可共享复现工具，不捏造缺陷或保证合并。

最终验证：运行 portable 与实际设备测试、独立性能轮次、site build/check、wheel/sdist 安装和快速上手；检查允许 API、来源归属、benchmark identity 与发布内容一致。按当前 checkpoint 更新进度，保留旧阶段证据。最终汇报四项：新增可用能力、相对两个基线的收益、DS 消融贡献、展示与上游候选。性能主目标未达成时明确保留为未完成，不能以工程项全部完成替代。
